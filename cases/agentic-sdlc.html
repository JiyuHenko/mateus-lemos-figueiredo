Engineering pattern · coding-agent workflows

Agentic SDLC Reference

A public distillation of the workflow patterns I use around coding agents such as Codex: explicit context, bounded authority, evidence-based validation and resumable execution.

The problem

Coding agents are useful because they can operate across many parts of a repository. The same flexibility creates risk: hidden assumptions, accidental refactors, stale context, false “done” states, expensive CI loops and side effects that are hard to audit.

My approach is to engineer the workflow around the agent instead of relying on a perfect prompt. The harness used on internal projects turns recurring engineering lessons into explicit rules, checks and source-of-truth files.

Core principles

Understand before editingInspect repository state, relevant files and existing user changes before touching code.
Classify the changeDistinguish spike, bounded change and architectural work so review depth matches actual risk.
Bound scope explicitlyDocument affected files, dependencies, risks and executable verification criteria.
Write success is not proofAfter important remote writes, read back the source of truth and verify the expected state actually persisted.
Green is not semantic correctnessA passing build, existing artifact or screenshot is evidence only when it proves the contract that matters.
Checkpoint long workPublish logical remote checkpoints so a later agent can resume from authoritative state rather than memory.
Fast loop, heavy final gateRun cheap checks during iteration and reserve expensive build/visual evidence for an explicit release candidate.
Turn failures into system knowledgeRecurring mistakes become a rule, automated check, reusable template or architectural change.

Reference lifecycle

1. Read repository + source-of-truth context
2. Preserve existing user changes
3. Classify change: spike / bounded / architectural
4. Write a small plan
   - problem
   - hypothesis
   - files
   - dependencies
   - risks
   - executable verification
5. Implement the smallest coherent unit
6. Validate near the real behavior
7. Run fast quality gates
8. Publish a remote checkpoint for long-running work
9. Read back remote writes when they matter
10. At release candidate:
    - full CI
    - build/export
    - security checks
    - visual QA / runtime evidence
11. Review diff + artifacts
12. Record what remains unverified
13. Convert recurring failures into harness improvements

Why “evidence” is a first-class concept

Agent workflows fail when status becomes a substitute for truth. A screenshot can show the wrong route. A file can exist but contain stale data. A deploy API can return success while the remote state differs from what was intended. A test suite can be green while it verifies the wrong contract.

The operating rule is simple: define what would actually prove the claim, then collect that evidence as close as possible to the real system.

Example: fast vs. full CI

On Project Fit, normal draft iteration uses a fast pull-request gate for lockfile integrity, linting, formatting, TypeScript, unit/integration checks and harness validation. Heavy exports and visual evidence run at an explicit final gate instead of every checkpoint.

This protects both quality and cost: the workflow does not weaken the release gate, but it avoids repeatedly paying for heavyweight evidence before a real release candidate exists.

Safety boundaries for AI-assisted product features

The same thinking applies inside products. On a current product, AI-generated interpretation is intentionally kept separate from canonical product authority. Factual progress, access control, billing, identity and other critical state remain server-authoritative; AI receives bounded context and cannot silently become the source of truth.

Where I want to push this further

  • Typed contracts between planning, implementation, review and deployment agents.
  • Stronger policy checks around side-effecting tools and secret-bearing operations.
  • Automated provenance linking claims to tests, screenshots, logs or remote read-back.
  • Reusable adoption patterns that engineering teams can understand, customize and teach internally.
  • Metrics that separate “more code produced” from actual developer throughput, reliability and review quality.
